# MySQL / MariaDB data preparation

The SQL scripts populate the database used by the `/api/v1` API. The frontend fetches
paginated species data through this API. JSON exports are used only for import
generation and tests. See [API setup and endpoints](api.md).

Target versions: MySQL 8.0.16+ or MariaDB 10.11+. Tables use InnoDB, foreign keys,
`utf8mb4`, and enforced check constraints. Select your website's existing database in
the SQL client or hosting control panel. The scripts do not create, alter, drop, or
select a database, and do not require permission to create one.

All 14 dex tables use the `emerald_ex_` prefix, for example `emerald_ex_species` and
`emerald_ex_moves`. Explicitly named constraints and indexes use the same prefix to avoid
constraint-name collisions with other projects in the shared database. Imports and
queries reference only these prefixed tables; other projects' tables are untouched.

Checks use column-level `CHECK` syntax because phpMyAdmin's static analyser can
misread named table-level checks. The validation rules remain enforced by the
database; names for these checks are generated by the server.

## Files and execution order

1. `scripts/sql/001_schema.sql` — prefixed tables, keys, constraints and indexes.
2. `scripts/sql/002_import_emerald_ex_1.0.4.sql` — prepared data import.
3. `scripts/sql/003_verify_import.sql` — counts and representative records.
4. `scripts/sql/004_api_query_examples.sql` — example queries for the proposed API.

The import files are generated from the four local exports and the battle sprite
manifest in `docs/`:

```bash
npm run db:generate-import
```

Generation validates game/version and ROM hashes, species IDs and names across exports,
stat totals, move references and repeated move attributes, type/category mappings,
evolution methods, TM/HM references, duplicate IDs/pairs, numeric ranges and exported
row counts. Validation finishes before the output file is written. The generator uses
built-in Node.js APIs and never connects to a database. Regenerate the SQL after editing
an export; JSON files are import inputs, not the API's runtime storage.
`npm test` also checks that the prepared SQL still matches the current source exports.
Sprite validation matches IDs/names to the species catalog, verifies availability,
variant/frame counts and relative filenames, and reads every referenced PNG to check
that it exists and has a 64×64 PNG header. Image bytes remain on disk; SQL stores the
relative filenames, frame count and the reason recorded for missing sprites.

### Upgrade an already imported database with sprites

Using an administrative SQL account, select your existing database and run:

1. `scripts/sql/005_species_sprites.sql` — creates `emerald_ex_species_sprites`.
2. `scripts/sql/006_import_sprites_1.0.4.sql` — replaces only sprite records and the
   `battle_sprites` source metadata for `emerald-ex-1.0.4` in one transaction.
3. `scripts/sql/003_verify_import.sql` — verifies all counts, including sprites.

Run the same upgrade in local development and in production before deploying the
updated API. The API account remains read-only and needs SELECT on the new table.
These scripts do not require a full data re-import or change existing species, moves,
learnsets, evolutions, machine compatibility, other datasets or unrelated tables.
Fresh setups use the updated `001_schema.sql` and `002_import_emerald_ex_1.0.4.sql`,
which already include sprites. Both upgrade scripts are repeatable; run them with
stop-on-error handling and roll back an unsuccessful data transaction.

For PowerShell:

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
Get-Content -Raw -Encoding utf8 scripts/sql/005_species_sprites.sql | mysql --default-character-set=utf8mb4 --batch -h localhost -u dex_admin -p YOUR_EXISTING_DATABASE
if ($LASTEXITCODE -ne 0) { throw 'Sprite schema creation failed' }
Get-Content -Raw -Encoding utf8 scripts/sql/006_import_sprites_1.0.4.sql | mysql --default-character-set=utf8mb4 --batch -h localhost -u dex_admin -p YOUR_EXISTING_DATABASE
if ($LASTEXITCODE -ne 0) { throw 'Sprite import failed' }
```

The generated file is intentionally included as a ready-to-run SQL artifact. Inserts
are batched into at most 250 rows per statement; no `LOAD_FILE`, JSON_TABLE, database
FILE permission, server-side source paths, or ORM is required.

### Run with the SQL command-line client

Examples below use the MySQL client name `mysql`; substitute `mariadb` for MariaDB.
Use your database user and host. `-p` prompts for the password without putting it in
the script or command line. Do not use `--force`: the batch must stop at the first error.

Replace `YOUR_EXISTING_DATABASE` below with the database your hosting provider supplies
(the same name you will configure as `DB_NAME`). No empty database is required.
For Bash or Windows Command Prompt, from the repository root:

```bash
mysql --default-character-set=utf8mb4 --batch -h localhost -u dex_admin -p YOUR_EXISTING_DATABASE < scripts/sql/001_schema.sql
mysql --default-character-set=utf8mb4 --batch -h localhost -u dex_admin -p YOUR_EXISTING_DATABASE < scripts/sql/002_import_emerald_ex_1.0.4.sql
mysql --default-character-set=utf8mb4 --batch -h localhost -u dex_admin -p YOUR_EXISTING_DATABASE < scripts/sql/003_verify_import.sql
```

For PowerShell, set UTF-8 pipeline encoding and stream each file to the client:

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
Get-Content -Raw -Encoding utf8 scripts/sql/001_schema.sql | mysql --default-character-set=utf8mb4 --batch -h localhost -u dex_admin -p YOUR_EXISTING_DATABASE
if ($LASTEXITCODE -ne 0) { throw 'Schema creation failed' }
Get-Content -Raw -Encoding utf8 scripts/sql/002_import_emerald_ex_1.0.4.sql | mysql --default-character-set=utf8mb4 --batch -h localhost -u dex_admin -p YOUR_EXISTING_DATABASE
if ($LASTEXITCODE -ne 0) { throw 'Import failed' }
Get-Content -Raw -Encoding utf8 scripts/sql/003_verify_import.sql | mysql --default-character-set=utf8mb4 --batch -h localhost -u dex_admin -p YOUR_EXISTING_DATABASE
```

If the client is not on PATH, use its full executable path. Never commit connection
credentials. In a hosting control panel such as phpMyAdmin, select the existing database
and import the schema followed by the data file; ensure errors stop the import and
roll back its transaction.

### Re-import behavior

Schema creation is repeatable with `CREATE TABLE IF NOT EXISTS`; it is not a migration
mechanism for changing an already-created table definition. DDL commits independently,
so apply it before importing data.

If you previously ran the unprefixed scripts, the revised schema creates a separate
set of prefixed tables and the import populates them from the exports. Existing
unprefixed tables are never renamed or dropped automatically because other projects
may own tables with those names. Confirm ownership before separately migrating or
removing any old tables.

The import starts one transaction, locks the dataset record, deletes that dataset's
rows in foreign-key order, and inserts the complete new snapshot. It commits only
after every INSERT succeeds. Re-running it replaces `emerald-ex-1.0.4` and leaves other
datasets and all tables outside `emerald_ex_` intact. Any error in a stop-on-error batch
closes the connection and rolls back the uncommitted replacement. An interactive client must issue `ROLLBACK` on error
and must not continue to `COMMIT`.

The script temporarily enables strict SQL mode and `NO_BACKSLASH_ESCAPES`, doubles
single quotes, and restores the prior SQL mode on success. Foreign keys stay enabled.
Additional tables referencing these records may prevent snapshot replacement; imports
remain an administrative operation, separate from the API's read-only user.

## Relational model

Every primary key includes `dataset_id`, so game versions can coexist without mixing
their internal IDs. Names are not species identities: multiple forms share a name.

| Table | Contents |
| --- | --- |
| `emerald_ex_datasets` | Game/version identity |
| `emerald_ex_sources` | Source filename, SHA-256 and extraction metadata |
| `emerald_ex_species` | Internal ROM species/form ID and display name |
| `emerald_ex_species_stats` | Six base stats and a generated total |
| `emerald_ex_species_sprites` | Standard/shiny front/back filenames, optional second front frames, frame count and missing-sprite reason |
| `emerald_ex_types`, `emerald_ex_species_types` | ROM type mapping and ordered species types |
| `emerald_ex_moves`, `emerald_ex_move_categories` | Full move records and category mapping |
| `emerald_ex_learnset_entries` | Species, original entry order, level and move reference |
| `emerald_ex_evolution_methods`, `emerald_ex_evolutions` | Directed evolution edges and trigger conditions |
| `emerald_ex_machines`, `emerald_ex_species_machines` | TM/HM definitions and species compatibility |

`emerald_ex_sources.metadata` and `emerald_ex_evolutions.conditions` are SQL JSON columns
for extraction notes and heterogeneous evolution requirements. Queryable species, stats, move fields,
learnsets and relationships live in relational columns, not serialized export blobs.
Conditions preserve raw item/move/map/party/nature information and `raw_param` without
inventing item or map catalogs that the supplied files do not contain.

The import uses the top-level evolution `edges` as the canonical relationship list;
the duplicated per-species `evolutions`/`preEvolutions` arrays are derived representations.
Learnset attributes repeated in the JSON are validated against the top-level `moves` and stored once.
Original learnset entry order and level 0 are preserved. Mono-types occupy one slot.
Move ID 0 (`-`) is retained as the ROM sentinel, without an auto-increment identity.

Expected 1.0.4 data: 1,523 species/forms, 935 moves, 23,729 level-up entries,
2,280 species/type rows, 58 machines, 32,358 compatibility pairs, 618 normal evolution
rules, and 26 internal form-routing markers. Type ID 9 (`Mystery`) is retained in the
19-entry type catalog even though no species currently uses it.

The sprite manifest has 1,523 records: 1,519 with standard and shiny sprites and four
with NULL filenames (species IDs 1431, 1432, 1433 and 1435). A second front frame exists
for 958 forms. Filenames are keyed by species/form ID, rather than deduplicated by name.

## API mapping

`004_api_query_examples.sql` illustrates the species/name/learnset/stats/types/evolution
and moves/name/category/pp/damage/type routes, plus TM/HM compatibility. The API
binds both the ID and a configured dataset (`emerald-ex-1.0.4` initially), even if
only the ID appears in the URL. Unknown species/move IDs return 404; valid species with
no learnset/evolution/machines return an empty array. Parse numeric IDs strictly, bound
list endpoints, and use driver parameters rather than string concatenation.

`/evolution` excludes `internal_only = 1`. Incoming edges are stored under
`to_species_id`; the `/details` response includes incoming rules and separately labelled
internal form markers. `/sprites` exposes the sprite references for a species.

The exported `power` is base move power. `/moves/:id/damage` and `/moves/:id/power`
return `{ data: { power: n, effectId: n } }`, rather than calculated in-battle damage.
`power = 0` and `accuracy = 0` retain their raw engine semantics: special/status damage
and no normal percentage accuracy check. Keep effect/target IDs for future battle logic.

[MariaDB JSON type](https://mariadb.com/docs/server/reference/data-types/string-data-types/json),
and [MySQL SQL modes](https://dev.mysql.com/doc/refman/8.0/en/sql-mode.html).

## Verification

The scripts were executed on an isolated MariaDB 12.0.2 instance on 2026-10-06.
Prefixed schema creation in a shared database, full import, repeated schema/import,
count checks and every API query example passed. All 13 existing unprefixed tables and
their row contents remained unchanged. Additional checks confirmed rollback after an
intentional foreign-key failure, preservation of another dataset, exact equality of
all 935 move records with the source, and rejection of invalid type slots, accuracy,
and base-stat ranges. The revised column-level checks were also tested in a fresh
schema with a full import and repeat import: invalid type slots, move accuracy,
learnset/evolution levels, machine kind/number, and internal evolution flags were
all rejected. phpMyAdmin sql-parser 5.11.1 reported zero errors for the revised schema
(the previous named table-level checks produced 14 parser errors). MySQL execution
has not been verified on a live MySQL instance.

The sprite schema/full import and repeated incremental upgrades were also verified
on an isolated MariaDB 12.0.2 instance. It retained an unrelated project's table and
returned all 1,523 sprite records with 1,519 standard and shiny front filenames.
